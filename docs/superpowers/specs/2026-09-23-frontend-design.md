# Frontend автопротоколирования совещаний

## Цель

Создать в `frontend/` автономный Next.js-интерфейс для одного основного сценария:
загрузить или записать встречу, дождаться обработки Java API, прочитать протокол и скачать PDF или DOCX.
Интерфейс не содержит регистрации, редактирования результата, проигрывателя, поиска, пагинации или прямых вызовов Python и внешних AI API.

## Источники требований

- Три приложенных пользователем скриншота задают композицию и визуальный характер.
- Приложенные локальные тексты задают Java DTO, состояния интерфейса и поведение записи.
- `AGENTS.md`, `PROJECT_STRUCTURE.md`, `FRONTEND.md` и `BACKEND.md` задают правила репозитория.
- Google Docs не используются: локальных контрактов достаточно для реализации.

## Технология и границы

Frontend создаётся на Next.js с App Router и TypeScript. Стили пишутся обычным CSS без внешних шрифтов, CDN и тяжёлого UI-фреймворка. Состояние остаётся в React, история — в безопасной обёртке над `localStorage`, сетевой слой — над стандартным `fetch`.

Меняется только `frontend/`, корневая документация запуска и `CHANGELOG.md`. Backend и AI service не изменяются.

## Визуальная система

Основной фон напоминает тёплую бумагу, весь интерфейс собран тёмно-бирюзовыми рамками. Жёлтый выделяет загрузку и экспорт, тёмный бирюзовый — запись, шалфейный — итог и спокойные статусы, коралловый — ошибки и активную запись.

Основные цвета:

- бумага: `#F5F1E6`;
- тёмный бирюзовый: `#073E3D`;
- основной текст: `#092F2F`;
- жёлтый: `#F1C75B`;
- шалфейный: `#DCE2D3`;
- коралловый: `#F47A68`.

Используется системный гротеск без сетевых загрузок. Таймер и таймкоды используют системный моноширинный набор. Углы сдержанно скруглены, тени мягкие, а декоративные квадраты повторяют фирменный мотив скриншотов. Анимация ограничена spinner, skeleton shimmer и реакциями на действия; при `prefers-reduced-motion` она отключается.

## Маршруты и композиция

### Главная `/`

Верхняя рамка содержит знак, название «ПРОТОКОЛ» и переключатель языка как статичный элемент оформления. Первый экран показывает заголовок «Из разговора — в протокол», две крупные панели «Загрузить файл» и «Записать встречу», затем компактные последние записи и переход ко всем пяти.

### Все записи `/meetings`

Экран повторяет третий скриншот: крупный заголовок, действия загрузки и записи справа и таблица максимум из пяти локальных ссылок. На мобильном таблица превращается в вертикальные записи без горизонтального скролла. Название открывает запись, а экспортные кнопки не запускают навигацию.

### Обработка и результат `/meetings/[id]`

Первый GET показывает skeleton только до получения начального ответа. `QUEUED` и `PROCESSING` показывают честный экран ожидания со статусом и `stage`, без процентов. `FAILED` показывает понятную ошибку и переход к новой загрузке. `COMPLETED` показывает заголовок, метаданные, саммари, расшифровку слева и поручения с проблемами справа. Пустые списки являются нормальным состоянием.

### Модальное окно записи

После разрешения микрофона открывается компактный диалог с предупреждением участников, красной точкой, реальным таймером, завершением и отменой. Фон, Escape и крестик не закрывают активную запись без подтверждения. После закрытия фокус возвращается к кнопке запуска.

## Архитектура frontend

- `app/` владеет маршрутами и общим каркасом.
- `components/` содержит визуальные элементы и доступные диалоги.
- `features/meetings/` содержит upload, polling, export, список и представление результата.
- `features/recording/` содержит выбор MIME, жизненный цикл `MediaRecorder`, таймер и освобождение tracks.
- `lib/api/` содержит DTO Java API, problem details и единственную точку сетевого доступа.
- `lib/storage/` хранит максимум пять ссылок `{id, accessToken, title, createdAt, expiresAt}` и переживает недоступность `localStorage`.
- Все данные поступают из Java API; frontend не содержит демонстрационных данных или mock transport.

Токены не попадают в URL или логи. API base URL читается из `NEXT_PUBLIC_API_BASE_URL`.

## Потоки данных

### Загрузка

Выбор одного MP3 или MP4 проверяет непустой файл, расширение и предел 500 MB, затем автоматически вызывает `POST /api/v1/meetings`. Пока используется `fetch`, показывается spinner без фиктивного процента. После `202` id и token сохраняются до перехода на страницу обработки. При неоднозначной сетевой ошибке POST не повторяется автоматически, а исходный File остаётся в памяти для ручной попытки.

### Запись

`getUserMedia` запрашивает микрофон, затем выбирается поддерживаемый контейнер через `MediaRecorder.isTypeSupported`. При старте запоминаются `startedAt` с offset и IANA timezone. Остановка дожидается последних данных, освобождает tracks и отправляет Blob с `source=MICROPHONE`. Ошибочный upload оставляет Blob для ручного повтора.

### Polling

Активная запись опрашивается каждые три секунды. Следующий GET начинается только после завершения предыдущего. Polling прекращается после `COMPLETED` или `FAILED` и очищается при размонтировании. Сетевая ошибка не меняет серверный статус и предлагает повторить GET.

### История

При старте читаются максимум пять ссылок и для каждой запрашивается актуальное состояние. `404` удаляет недоступную ссылку; сетевой сбой сохраняет её. Шестая запись вытесняет самую старую локальную ссылку. Срок считается только по `expiresAt`, а `null` не считается истёкшим.

### Экспорт

PDF и DOCX доступны только при `COMPLETED`. Запрос передаёт Bearer token в заголовке, проверяет тип ответа, создаёт временный object URL и освобождает его после запуска скачивания. Ошибка остаётся рядом с выбранным форматом и не закрывает результат.

## Ошибки и доступность

`application/problem+json` отображается по `code`, без показа стеков и без разбора `detail` как управляющей логики. Отдельно покрываются 400, 404, 409, 413, 415, 422 и 503. Все кнопки имеют текстовые подписи, видимый focus, честные disabled/loading состояния. Диалоги и меню работают с клавиатуры. Во время записи и не завершившейся загрузки устанавливается стандартное предупреждение `beforeunload`.

## Проверка

Проектные правила запрещают добавлять тестовую инфраструктуру без отдельного запроса. Проверка включает:

- установку зависимостей и production build;
- TypeScript и lint, если они настроены проектом;
- ручные сценарии загрузки, записи, отмены, polling, ошибки, результата и экспорта;
- desktop и mobile размеры, клавиатуру и reduced motion;
- финальный `review-against-task` в Code Rules и task-compliance режимах.

Функции, требующие настоящего Java API, будут явно перечислены в README и финальном отчёте.
